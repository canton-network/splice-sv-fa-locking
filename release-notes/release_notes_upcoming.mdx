## Upcoming for next patch release:

{/* Add all release notes in this section */}

  - Scan App

    - Removed the internal `/v0/transfer-command-counter/{party}` and `/v0/transfer-command/status` endpoints.
      Most of the deprecated TransferCommand functionality has already been removed in splice 0.8.0, this removes
      the remaining parts.
    - Removed the deprecated `/v0/amulet-config-for-round` endpoint. Use the `transferConfigUsd` and `amuletPrice`
      fields of the `OpenMiningRound` contracts returned by `/v0/open-and-issuing-mining-rounds` instead.

  - Validator App

    - Removed the `/v0/scan-proxy/transfer-command-counter/{party}` and `/v0/scan-proxy/transfer-command/status`
      endpoints. Most of the deprecated TransferCommand functionality has already been removed in splice 0.8.0,
      this removes the remaining parts.

  - SV App

    - SVs now run `ExecuteFeaturedAppUnderlockInstructionTrigger`, which
      applies each `FeaturedAppUnderlockInstruction` to the featured app
      right of its provider, suspending or unsuspending the right.

    - Support changing the `governanceLockManagementConfig` fields in `DsoRules` config vote requests.

    - SV app automation now detects featured app providers whose full featured app locks are below the
      lock threshold of their app kind, and votes to suspend their featured app right, or to lift the
      suspension once they lock enough. It only acts while `featuredAppUnderlockEnforcementEnabled` is set in
      the `governanceLockManagementConfig` of the `DsoRules` config, and checks every minute by default
      (`featured-app-underlock-status-update-interval`).

    - SV app automation now archives a suspended featured app right once its underlock grace period
      has passed, while `featuredAppUnderlockEnforcementEnabled` is true.

    - SV app automation now executes `RevokeFeaturedAppRightInstruction`s, archiving the provider's
      featured app right. It also archives instructions that expire before they are executed.

  - Governance locks

    - The `cip-127/*` metadata entries (e.g. `cip-127/lock-kind` and `cip-127/lock-status`), which were created by accident in the metadata, are no longer
      written to the metadata of governance lock transfer instructions and of lock transfer and substitution proposals.
      Read the lock information from the `cip-127/memo:` memo in the reason
      (`splice.lfdecentralizedtrust.org/reason`) instead.

    Details:

    - Daml Model Changes:

      - Add underlock enforcement for featured app rights, as specified in
        [CIP-127](https://github.com/canton-foundation/cips/blob/main/cip-0127/cip-0127.md).
        A featured app provider that does not keep enough Amulet locked loses its featured status:

        - Add the optional `underlockPermanentAt` field to `FeaturedAppRight`. If it is set, the featured app right is suspended:
          `FeaturedAppRight_CreateActivityMarker` creates no activity markers,
          and transfers do not record the provider as a featured app provider.

        - Add the `SRARC_CreateFeaturedAppUnderlockInstruction` vote action. It creates a `FeaturedAppUnderlockInstruction`
          that records that SVs observed a provider to be underlocked, or to have recovered from an underlock.
          SVs execute it with `DsoRules_ExecuteFeaturedAppUnderlockInstruction`, which sets
          `underlockPermanentAt` to the end of the grace period, or clears it after a recovery.

        - Add `DsoRules_EnforceFeaturedAppPermanentUnderlock`, which archives a suspended featured app right
          after its `underlockPermanentAt` deadline passes.

        - Add the `SRARC_CreateRevokeFeaturedAppRightInstruction` vote action. It creates a `RevokeFeaturedAppRightInstruction`,
          which SVs execute with `DsoRules_ExecuteRevokeFeaturedAppRightInstruction` to archive the featured app right of a provider.

            This is required to ensure that revocation votes do not refer to the featured app right by its contract-id, which risks
            the votes becoming stale as the right may be mutated, which results in a new contract-id. The existing
            `SRARC_RevokeFeaturedAppRight` action is susceptible to this risk, and is therefore deprecated.

        - Both instruction templates expire after the vote request timeout.
          SVs archive expired instructions with `DsoRules_ExpireFeaturedAppUnderlockInstruction`
          and `DsoRules_ExpireRevokeFeaturedAppRightInstruction`.

      - Add the optional `governanceLockManagementConfig` field to `DsoRulesConfig` with these fields:

        - `featuredAppUnderlockEnforcementEnabled` (default false)
        - `featuredAppBasicLockThreshold` (default 5M CC)
        - `featuredAppAssetMovingLockThreshold` (default 5M CC)
        - `featuredAppAssetLockThreshold` (default 25M CC)
        - `featuredAppUnderlockGracePeriod` (default 7 days)

      - Add custom controllers to governance locks, as specified in
        [CIP-127](https://github.com/canton-foundation/cips/blob/main/cip-0127/cip-0127.md).
        A lock can name custom controllers for unlocks, substitutions and vesting, instead of the lock owner alone.
        Each of these three actions has its own optional controllers specification.
        A controllers specification is a list of party sets. An action is approved once all parties
        of any one set approve it.

        - Locks without custom controllers continue to work as before: the owner alone controls them,
          unlocks and vested fund withdrawals execute immediately, and transfers and substitutions need
          the same approvals as before.

        - For each action that has custom controllers, these controllers replace the owner.
          The owner can no longer do that action alone, unless the owner forms a controller set alone.
          A transfer always needs the approval of the owner as well.

        - Unlocks, vested fund withdrawals, transfers, and substitutions of governance locks with custom controllers
          are now proposals that the controllers of the lock approve. A proposal executes as soon as all parties of one
          controller set accept it. If the parties that create the proposal already form a controller set,
          the proposal executes immediately.

        - While a proposal is pending, the parties vote on it with the Token Standard V2
          `TransferInstruction_Accept`, `TransferInstruction_Reject` and `TransferInstruction_Withdraw` choices.
          Each choice takes a list of actors, so several parties can vote jointly in a single choice exercise.
          The parties that created the proposal (the proposers) count as accepting it.
          Who can exercise each choice:

          - `TransferInstruction_Accept`: any controller that has not accepted yet. This includes a controller
            that rejected earlier, and a proposer that withdrew earlier.
          - `TransferInstruction_Reject`: any controller that has not voted yet, and any controller that accepted
            and is not a proposer. Proposers cannot use this choice.
          - `TransferInstruction_Withdraw`: any proposer that currently accepts the proposal.
            It records a rejection for that proposer.

          A proposal is rejected and archived once all proposers withdraw it,
          or once every controller set contains a rejection.

        - Each proposal expires after the `tokenStandardMaxTTL` of the transfer config (default 90 days),
          counted from its `requestedAt` time. An unlock proposal expires earlier at its `vestingStartTime`,
          and a transfer or substitution of a vesting lock expires earlier at the end time of the lock.
          An expired proposal can no longer be accepted, but it can still be rejected or withdrawn.
          SV automation archives expired proposals.

        - Unlock and withdrawal proposals can be dated in the future, so that the controllers have time to approve them:

          - The `vestingStartTime` of an unlock can be up to 90 days in the future if the lock has
            custom unlock controllers, and up to 1 day if it is owner controlled. It must still be in the future
            when the proposal executes.
          - The `vestedUntilTime` of a withdrawal can be in the future when the proposal is created.
            It must be in the past when the proposal executes.

        - The proposers of a governance lock transfer set the custom controllers of the new lock
          that the transfer creates for the receiver.
          Receivers are expected to review these new controllers before they accept the transfer.

        Implementation details:

        - Add the optional `unlockControllers`, `substitutionControllers` and `vestingControllers` fields
          to `FullLockSpecification`, and the optional `vestingControllers` field to `VestingLockSpecification`.
          If a field is not set, the lock owner alone controls the action.
          A full lock passes its `vestingControllers` on to the vesting lock that an unlock creates.

        - Lock requests set the controllers with the `unlock-controllers`, `substitution-controllers`
          and `vesting-controllers` memo keys. Transfer and substitution requests set the controllers of
          the resulting lock with the `new-unlock-controllers`, `new-substitution-controllers` and
          `new-vesting-controllers` memo keys. The values are JSON lists of lists of parties.
          A vesting lock accepts only vesting controllers.

        - Unlock, withdrawal and transfer requests on a lock with custom controllers name the lock owner
          with the `target-lock-owner` memo key, so that a controller other than the owner can send the request.
          Substitution requests always name the owner of the target lock with this key.

        - The proposal templates and their controllers:

          - An unlock request creates an `UnlockProposal`, controlled by the unlock controllers.
          - A withdrawal request creates a `WithdrawVestedFundsProposal`, controlled by the vesting controllers.
          - A `GovernanceLockTransfer` needs the approval of the source lock owner, the receiver and one set of
            the substitution controllers (vesting controllers for a vesting lock).
          - A `GovernanceLockSubstitution` needs the approval of the party whose funds back the substitution,
            who must be one of the proposers, and of the owner of the target lock or one set of its substitution controllers (vesting controllers for a vesting lock).

        - Each proposal implements the `TransferInstruction` V1 and V2 interfaces.
          `UnlockProposal` and `WithdrawVestedFundsProposal` do not support the V1 accept and reject choices.
          A pending proposal is archived and created again with the updated votes on each vote.
          The new contract links to the first one through `originalInstructionCid`.

        - The proposals deviate from CIP-127 in these points:

          - An `UnlockProposal` takes the `vestingStartTime` only when the proposal is created,
            not from each controller that approves it.
          - A `WithdrawVestedFundsProposal` takes the `vestedUntilTime` only when the proposal is created,
            not from each controller that approves it.
          - A `GovernanceLockTransfer` takes the custom controllers of the new lock only when the proposal is created,
            not from the receiver that becomes the owner of the new lock.
          - Custom controllers can also be set with memo keys in the Token Standard transfer request,
            in addition to the specification fields. These memo values can be large.

        - Add the `GovernanceLock_DsoMerge`, `GovernanceLock_DsoUnlock`, `GovernanceLock_DsoWithdraw`,
          `GovernanceLock_DsoSubstitute`, `GovernanceLock_DsoSplitForSubstitution` and `GovernanceLock_DsoTransfer`
          choices, which approved proposals use to act on a lock with the authority of the DSO party.

        - Add the `DsoRules_UnlockProposal_DsoExpire` and `DsoRules_WithdrawVestedFunds_DsoExpire` choices,
          which SVs use to archive unlock and withdrawal proposals after they expire. Expired transfers and
          substitutions continue to use `DsoRules_GovernanceLockTransfer_DsoExpire` and
          `DsoRules_GovernanceLockSubstitution_DsoExpire`.
